# v0.1a Fallback Spec

> Optional but recommended: the degraded-mode acceptance path for v0.1.

---

## Purpose

v0.1a tests that the system handles solver failures gracefully — the degraded mode path. This is a secondary acceptance scenario, not a substitute for v0.1 (which requires the live solver path to succeed).

---

## Scenario

Same as v0.1 (motor mount bracket), but the CalculiX wrapper is configured to fail on every attempt (injected failure). Degraded mode activates after 3 consecutive failures, per AC-01a.

---

## Acceptance Criteria

### AC-01a: Degraded Mode Activation
- [ ] After 3 CalculiX failures, `SWITCH_STUB_SOLVER` activates
- [ ] Activation logged with event `tactical_switch_activated`

### AC-02a: Stub Result
- [ ] Stub solver output contains placeholder values
- [ ] Stub output contains flag: `degraded: true`
- [ ] Gap flags added: `"FEA result requires live solver verification"`

### AC-03a: Verification with Stub
- [ ] Contract Gate passes (stub output is contract-compliant)
- [ ] Unit Gate passes (stub output has units)
- [ ] Provenance Gate: warn (stub source is `"stub"`)

### AC-04a: Vault Write Degraded
- [ ] Note written with `status: degraded`
- [ ] Note flagged for manual review
- [ ] Amnesia check passes

### AC-05a: Output Report Degraded
- [ ] Output status: `degraded`
- [ ] Unresolved gaps include: `"FEA result requires live solver verification"`
- [ ] Human review flag set in output

### AC-06a: JSONL Log
- [ ] `SWITCH_STUB_SOLVER` activation in log
- [ ] All tool error events logged with error_codes
- [ ] Degraded result not presented as full-confidence result
