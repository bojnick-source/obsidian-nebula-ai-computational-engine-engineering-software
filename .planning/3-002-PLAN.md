## Objective

Add `forge_agent/tests/test_v01_acceptance_live.py` — a second acceptance test
suite that runs the **complete 9-phase PipelineRunner** using `LiveToolExecutor`
and a real `ObsidianVaultManager` (tmp_path), with **no mock tool executor**.

In the Phase 3 CI environment (gmsh pkg absent, ccx binary absent), `LiveToolExecutor`
will return proper `error_envelope()` dicts with `status="error"` and
`error_code="ERR_TOOL_SUBPROCESS_FAIL"`. The pipeline detects these envelopes,
sets `blackboard["tool_execution.degraded"] = True`, and produces
`TaskResult.status == "degraded"`.

This suite proves that all 10 AC behaviours hold in the degraded environment —
vault is still written, frontmatter is correct, JSONL has 9 phases, amnesia_check
passes, trace IDs propagate, etc.

## Design

### Key insight: envelope detection in pipeline

`PipelineRunner._run_phase_tool_execution()` currently checks:
```python
if gmsh_result.get("status") == "degraded" or ccx_result.get("status") == "degraded":
    overall_status = "degraded"
```

`LiveToolExecutor` returns `error_envelope(...)` which has `status="error"` (not
`"degraded"`). The test suite must handle this correctly. There are two approaches:

**Approach A** (no pipeline change): Verify that `status in {"degraded", "error"}`
counts as degraded. The tests assert `result.status in {"degraded", "complete"}` —
they do NOT assert exactly `"degraded"`, since the pipeline only sets `degraded`
when `status == "degraded"`. With `status="error"`, `_assemble_output()` will see
`tool_execution.degraded` is False and verification may pass → `result.status`
could be `"complete"`.

**Approach B** (correct): The pipeline checks envelope status broadly. Looking at
`pipeline.py` line 437:
```python
if gmsh_result.get("status") == "degraded" or ccx_result.get("status") == "degraded":
    blackboard["tool_execution.degraded"] = True
```
This only triggers on `"degraded"`, not `"error"`. To close this gap without
changing pipeline.py, `LiveToolExecutor` should return envelopes with
`status="degraded"` (not `status="error"`) when tools are absent — achieved by
passing `status="degraded"` to `error_envelope()`.

**Resolution**: 3-001 must ensure `LiveToolExecutor` calls
`error_envelope(..., status="degraded")` for absent-tool cases. The 3-002 tests
then rely on that contract. Document this dependency explicitly.

### File structure

```python
# forge_agent/tests/test_v01_acceptance_live.py

from forge_agent.core.live_tool_executor import LiveToolExecutor
from forge_agent.core.pipeline import PipelineRunner, TaskRequest
from forge_agent.memory.obsidian_manager import ObsidianVaultManager

def _make_live_runner(tmp_path, anthropic_client=None):
    vault_manager = ObsidianVaultManager(vault_path=tmp_path)
    return PipelineRunner(
        config={"provider": "anthropic"},
        tool_executor=LiveToolExecutor(),
        vault_manager=vault_manager,
        anthropic_client=anthropic_client,
    )
```

The `anthropic_client=None` path uses `_stub_specialist()` in the pipeline,
which returns `VALID_SPECIALIST_OUTPUT` — a contract-valid dict. This means
verification passes, and the only reason for `status="degraded"` is the
tool envelopes.

## Known Risks

- **Dependency on 3-001**: This plan cannot be executed until `LiveToolExecutor`
  exists and returns envelopes with `status="degraded"` for absent tools.
- **Status resolution**: If `LiveToolExecutor` returns `status="error"` instead
  of `status="degraded"`, the pipeline will not set `tool_execution.degraded=True`
  and `result.status` will be `"complete"` instead of `"degraded"`. Test 8
  (`test_live_degraded_status_when_tools_absent`) will catch this regression.
- **Language**: Python only. MCP tool dispatch and test code; polyglot doctrine
  permits Python for both.
